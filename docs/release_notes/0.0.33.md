# 0.0.33

## What's New

- You can now share a single event from a public Calee calendar. Open the event
  to see its details and tap **Share event** to hand your phone's share sheet a
  link that opens exactly that occurrence — and it works the same whether you
  are signed in or following the calendar as a guest.
- Tapping any event on the calendar now opens the same event details view, with
  the actions that genuinely apply to it. A calendar you can both write to and
  share no longer loses the share option, and events from a followed calendar
  now show their full details instead of a short guidance message.
- Events from Google calendars no longer say they can be edited in Google
  Calendar, because Calee cannot open the event there.
- Followed public calendars now show changed and cancelled occurrences of a
  repeating event correctly. A moved occurrence appears once, at its new time,
  instead of twice, and a cancelled occurrence disappears instead of sitting
  beside the event it was meant to cancel.
- Repeating events from a calendar in another timezone keep their correct local
  time across a daylight-saving change.

## Internal notes

- Signed-out ICS parsing was reworked from "emit at every `END:VEVENT`" to
  parse → group by source UID → expand → reconcile → emit
  (`lib/features/calendar/local_subscriber/local_calendar_ics_service.dart`).
  `RECURRENCE-ID` (with its parameters) and `STATUS` are now parsed, so a
  detached override replaces the generated occurrence sharing its identity and a
  detached `STATUS:CANCELLED` component suppresses it. `LocalCalendarEvent`
  carries explicit source identity (`uid`, `recurrenceId`); the UID is treated as
  opaque and preserved byte for byte. DAILY/WEEKLY expansion now advances
  wall-clock time in the source TZID rather than adding a fixed `Duration` to a
  UTC instant, fixing the DST drift that gave every occurrence past a boundary
  the wrong identity. PR #560.
- Canonical occurrence identity
  (`local_calendar_occurrence_identity.dart`) is verified against the shared
  contract fixture at
  `contracts/event-occurrence-identity/v1/contract.json`, byte for byte with
  calee-hub-core and calembed: `Ymd` for all-day (never routed through a timezone
  conversion) and `YmdTHisZ` at the true UTC instant for timed occurrences. The
  contract test is green under `Australia/Perth`, `UTC`, `Pacific/Kiritimati` and
  `America/New_York` with the fixture hash unchanged. PR #561.
- Event Link minting (`local_event_link_service.dart`,
  `signed_in_event_share.dart`) POSTs exactly `{calendarUrl, uid}` plus
  `occurrenceId` for a recurring occurrence to the unauthenticated CalEmbed
  `/event-link` endpoint — no auth header, no session, no event content, no
  device identifier — with finite timeouts, redirects disabled, a 64 KiB response
  cap and no logging of the URI (it carries the public calendar token).
  `calee_public_calendar_source.dart` re-validates the RAW stored URL against the
  registered public-calendar shape before any share action is offered; it is a UX
  and privacy guard, and CalEmbed remains the sole authority on what may be
  minted. PRs #562, #563.
- `lib/features/calendar/event_capabilities.dart` derives edit, delete and share
  eligibility independently from the exact `ClientEvent`/`ClientCalendar`, fixing
  the early return in `CalendarPage._onDisplayEventTap()` that let write access
  suppress Share. `CalendarDisplayEvent` remains presentation-only and gained no
  source identity; row lookup goes through an identity map rather than the
  non-normative `LocalCalendarEvent.id`, which can collide for UIDs differing only
  in boundary whitespace. PR #567, fixes #566.
- Version: `build_number` is bumped to 33. Both stores permanently reject a
  re-used build number, so the number is bumped rather than re-cut.
- Release readiness: `docs/release_evidence/0.0.33.json` is deliberately absent.
  It attests that a named Release Operator prepared this release's listing,
  privacy disclosures and review notes, and that a named Release Approver signed
  off; it cannot be produced by tooling. Signed release builds off `stage`/`main`
  therefore fail closed until the operator completes it — see section 3.1 of
  `docs/RELEASE_OPERATIONS.md`.

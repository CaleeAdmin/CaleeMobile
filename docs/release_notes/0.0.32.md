# 0.0.32

## What's New

- Meal suggestions now work the same way everywhere you choose a meal: family
  favourites, recently used meals and quick dinner ideas appear in the same
  groups and the same order in Pick dinner, Saved Meals and meal search,
  starting with a short list you can expand with **More**.
- You can search your meals when picking dinner — by meal name or the notes you
  saved with it — including quick dinner ideas from outside the week you are
  looking at. If nothing matches, you can create the new meal straight from the
  search.
- Choosing a suggested meal now keeps it linked to the saved meal it came from,
  so your favourites and recently used lists stay accurate.
- Meals are now added from the day you are planning, or from Pick dinner. The
  separate **+** button at the top of the Meals screen has been removed.

## Internal notes

- Meals: Family favourites, Recently used and Quick dinner ideas are resolved by
  one shared resolver (`lib/features/meals/meal_suggestion_resolver.dart`) and
  rendered by one shared section widget, so grouping, ordering, the initial
  result limit and progressive `More` expansion no longer differ between Pick
  dinner, Saved Meals and search. Selecting a reusable meal preserves its saved
  or starter template linkage. The global top-right `Add meal` (`+`) action and
  its manual form were removed by product decision; the date-row add actions and
  Pick dinner's create-new path remain. PR #548, fixes #508.
- Release and CI tooling only, with no effect on app behaviour: signed Android
  builds may now be dispatched from any branch so a change can be exercised on a
  real device, but only a run from `stage`/`main` with completed readiness
  evidence is a release candidate (#550); the APK signing identity is now parsed
  by `scripts/read_apk_signing_identity.sh`, which keys off the stable part of
  the `apksigner` certificate lines rather than a build-tools-specific label
  prefix; and GitHub Actions consumption was cut across all four workflows
  (#553).
- Version: `build_number` is bumped to 32 rather than reusing 31. No release
  evidence file exists for 0.0.31, so no signed release candidate was produced
  from it through the documented path — but both stores permanently reject a
  re-used build number, and the 0.0.31 notes do not describe the meals changes
  now on `main`, so the number is bumped rather than re-cut.
- Release readiness: `docs/release_evidence/0.0.32.json` is deliberately absent.
  It attests that a named Release Operator prepared this release's listing,
  privacy disclosures and review notes, and that a named Release Approver signed
  off; it cannot be produced by tooling. Signed release builds off `stage`/`main`
  therefore fail closed until the operator completes it — see section 3.1 of
  `docs/RELEASE_OPERATIONS.md`.
